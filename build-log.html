One kit,
many labs

LabKit is a lean, zero-dependency template for virtual education labs: one shared core, a catalog of composable laws, and four labs that differ only by their data. This is how it was built — and how Kiro changed the way I develop.

By Gaia Samama-Giudicelli · Written as part of the Kiroween 2026 hackathon · Try the labs · Repository

The problem

Educational simulations usually come in two flavours, and both are wrong for a classroom. Heavy SDKs demand an install, an account and a modern laptop. One-off apps are closed boxes: a teacher can look at a gravity simulation but cannot turn it into a chemistry lab without starting over. Meanwhile the loop that actually teaches — hypothesis, action, observation, understanding — needs very few tools: a scene, a handful of sliders, live measurements, and the freedom to break things safely.

So the brief I set for Kiroween's Skeleton Crew track was narrow on purpose: build a template lean enough to be read, flexible enough to carry very different subjects, and prove it with labs that share nothing but the kit.

What is in the box

Four labs ship today, each a standalone HTML file a student can double-click — no server, no network, no account:

  • Space Lab (2D) — a gravity well, planets and an asteroid belt.
  • Eco Lab (2D) — rabbits, foxes and bushes, with a live population chart.
  • Chemistry Lab (3D) — real aqueous chemistry: eight reagents, burette titration, pH, precipitates and gas pressure.
  • Bridge Lab (3D) — ten structural materials, generated levels, a load ladder and a purse that carries over between bridges.

The kit itself is a core/ that knows zero science — layout, theme, sliders, instruments, notebook, validation — plus swappable engines and labs that are nothing but a config.json and a few dozen lines of glue. There is no dependency, no bundler, no framework. A new lab costs a copy, a config and a validation.

How Kiro changed the way I develop

I used to write code and backfill documentation when someone asked. Kiro inverted that: in this project the documents came first and the code had to obey them, and it is visible in the repository, not just claimed in a README.

  • Spec-driven development. Every module started as EARS requirements ("WHEN… the system SHALL…") in .kiro/specs/, then a design, then tasks. The acceptance criteria were not decoration: each one became a property test, run on every change.
  • Steering instead of repeated corrections. The rules I would normally repeat in review comments — the core never names a scientific concept, failure is free and names the offending value, laws never touch the DOM — live in .kiro/steering/ and are read by the agent before it writes anything.
  • A hook that actually bites. A PreToolUse guard runs the validator, the property tests and the standalone build before any commit or push, and blocks the tool call on failure. The same gate runs in CI, so nothing ships that would not pass — including a stale dist/.
  • Property-based testing found what I would have missed. Dozens of properties derived from the requirements, with seeded RNG and shrinking: alignment bugs in row matching, off-by-one in the law catalog, config drift — caught by generated cases, not by my imagination.
  • The whole surface. A local MCP server with five tools, four custom agents (lab-architect, law-smith, config-doctor, lab-reviewer), three skills, three workflows, and an installable power — all verifiable in CI by anyone who clones the repo.
The one sentence I would keep: the acceptance criteria mattered more than the design documents, because each one became a test that runs on every save. Writing "WHEN this, the system SHALL that" before typing is now how I start every feature, with or without an agent in the loop.

Why build-time only

Kiro built the kit; the labs do not need it. Everything runs offline, without credits, keys or a backend — a teacher on a classroom laptop with no wifi gets the same experience as a judge on a fiber connection. That constraint shaped the architecture: no runtime service, no telemetry, no install step, and standalone files regenerated in one command whenever a config changes.

Try it

The portal with all four labs is at gaiasg94.github.io/LabKit; each lab also exists as a double-clickable standalone file. The full source, specs and tests are on GitHub, MIT licensed. Non-developers get a step-by-step French guide, CREER-UN-LABO.md, to create a lab by editing JSON — no code, no Node.
