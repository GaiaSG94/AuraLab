# Steering — Architecture

Project-wide rules for any agent or contributor working in this repo.

## The core stays generic

`core/` must never import from `app-*/` or `engines/*`, and must never name
planets, rabbits, foxes, flasks or bridges. Every lab-specific concept lives
in a config, a wiring file or a law module.

If a lab seems to need a new core branch, the right move is to **extend the
schema for all labs** (`core/validate.js` + `core/catalog.js` + the docs),
never to add a lab-specific `if`.

## Single source of truth for the schema

`core/validate.js` is the only place where a config is checked. The browser,
the Node validator, the property tests and the MCP server all import it.
Never duplicate a range check, never validate in two places.

## Auto-tune, don't crash

Bad numbers get clamped or reset with a warning. Only structural violations
(missing title, unknown reference, broken control path, particle cap
exceeded) are errors, and every error must **name the offending value**.

## Two kinds of lab, one core

- **Shell labs** (`app-space`, `app-eco`): `core/shell.js` renders the whole
  page (steps | bench | panel). The lab only provides `buildLab()`.
- **Custom-UI labs** (`app-chimie`, `app-ponts`): they boot through
  `core/headless.js`, mount their own interface (3D canvas + HUD) and drive
  the loop themselves. They still use the same validator, the same catalog,
  the same notebook model.

A third kind is not allowed without a spec. If a lab needs its own interface,
it still shares the config schema, the catalog and the measurement contract.

## Laws are pure modules

A law module exports `{ id, notice, defaults, apply(world, dt, params, targets, active) }`
(or `place(world, p, def)` for an initial placement law). It never touches the
DOM (REQ-15) — that is what lets the tests run it in Node. It carries a
notice with the rule, the sources and the limits: a law without a notice is
incomplete.

## Zero dependency, no build step

Any static file server must serve the repo as-is. Do not add npm packages,
bundlers, frameworks or a `package.json`. `dist/` is generated by
concatenation, not by a bundler.

## Keep it small and readable

This template is judged on cleanliness. Prefer deleting code over abstracting
it. Files stay under 500 lines, functions under 50 lines. A file that grows
past the limit is split by responsibility, not by line count.

## The Kiro layer is part of the product

The methodology is a judged criterion, so it must stay real:

- a change to behaviour starts as a spec (`.kiro/specs/`), not as a patch;
- a change to a convention goes to `.kiro/steering/`;
- a change to the catalog goes to the pack manifest and its notice;
- a property test must exist for any new invariant (REQ-numbers are quoted
  in the test names);
- the standalone files in `dist/` are rebuilt and committed with the change.

## Before you push

```powershell
node scripts/validate-config.mjs
node scripts/build-standalone.mjs
node tests/run-tests.mjs
python3 .github/hermes/ci_fmt.py
```

`dist/` must be rebuilt and committed: CI fails when it drifts.
